# Native Arch Install for Agent Orchestrator — Implementation Plan

> **For agentic workers:** implement task-by-task; each task ends with a green test or a proven manual check, plus a commit. Steps use `- [ ]`.

**Goal:** Install AO on Arch Linux as an ordinary application — a launcher entry you click, `agent-orchestrator` and `ao` on `PATH`, `pacman` owning the files — so nobody has to keep a downloaded `.AppImage` around and launch it by hand.

**Branch:** `feat/linux-packaging`, cut from `Aoagent/main` @ `52fde0279`. PR target `main` on `Untrivial-ai/agent-orchestrator`.

## Why this is needed

Linux packaging is not greenfield. `frontend/forge.config.ts` already produces an AppImage (via the custom `frontend/makers/maker-appimage.ts`), a `.deb` and an `.rpm`, and `.github/workflows/build-artifacts.yml` builds all three for `linux-x64` on every release. `frontend/scripts/feed.mjs` publishes `latest-linux.yml` so the AppImage self-updates.

What is missing is a first-class Arch path. Today an Arch user downloads `agent-orchestrator-linux-x64.AppImage` and either runs it from the download directory or hand-writes a desktop entry pointing at wherever the file landed. The current working setup on the author's machine is exactly that:

```ini
# ~/.local/share/applications/AO-Agent.desktop
Exec=xdg-terminal-exec --app-id=TUI.tile -e ~/Downloads/Piyush/agent-orchestrator-linux-x64.AppImage
```

That entry is fragile (an absolute path into `~/Downloads`), and it wraps a GUI app in a terminal launcher. It also does not put `ao` on `PATH`, so the CLI documented in `CLAUDE.md` (`ao preview <url>`) is unavailable.

The desktop entry `ao start` writes is deliberately not a fix: `backend/internal/cli/start.go` sets `NoDisplay=true` on it, because it exists only to register the `x-scheme-handler/ao-app` protocol, not to appear in a launcher.

## Decision: repackage the released `.deb`, do not build from source

The AUR package is a `-bin` package that unpacks the published `agent-orchestrator-linux-x64.deb` from the GitHub release and re-lays its contents into the Arch prefix.

Rationale:

- The `.deb` is already FHS-correct. `electron-installer-debian` (via `@electron-forge/maker-deb`) installs the app under `/usr/lib/<name>/`, symlinks `/usr/bin/<name>` at the executable, writes `/usr/share/applications/<name>.desktop`, and copies icons into `/usr/share/icons/hicolor/<res>/apps/`. That is the layout an Arch package wants, so `package()` is mostly a move.
- Building from source would mean a full Go daemon build plus an Electron/npm build plus `prepare-agent-browser.mjs` and `build-acp-runtime.mjs` — hundreds of megabytes of `node_modules` and a bundled Chromium download inside `makepkg`. Not worth it for a desktop app whose upstream already publishes binaries.
- Extracting the AppImage instead of the `.deb` is possible but strictly more work: the AppDir has its own layout that must be translated, whereas the `.deb` already matches.

**Rejected alternative:** shipping a wrapper `.desktop` that points at a downloaded AppImage in a stable location. It solves the launcher entry but leaves the binary unmanaged, `ao` off `PATH`, and uninstall manual.

## File structure

All new files live in a new top-level `packaging/arch/` directory. Nothing under `frontend/` or `backend/` changes except the updater gate in T5.

| File                                            | Status | Responsibility                                                        |
| ----------------------------------------------- | ------ | --------------------------------------------------------------------- |
| `packaging/arch/PKGBUILD`                       | create | The `agent-orchestrator-bin` package definition                       |
| `packaging/arch/agent-orchestrator-bin.install` | create | `post_install`/`post_upgrade` hooks (icon + mime cache, sandbox note)  |
| `packaging/arch/.SRCINFO`                       | create | Generated by `makepkg --printsrcinfo`; required by AUR                 |
| `packaging/arch/README.md`                      | create | How to build, install, and publish this package                       |
| `packaging/arch/update-pkgbuild.sh`             | create | Bump `pkgver` + `sha256sums` from the latest GitHub release           |
| `frontend/src/main.ts`                          | modify | Skip the auto-updater when the install is package-manager owned (T5)  |
| `frontend/src/main/auto-updater.ts`             | modify | Same gate, unit-testable helper                                       |
| `README.md`                                     | modify | Add an Arch row to the install table                                  |

## Global constraints

- No em dashes anywhere (prose, comments, copy). Use `.`, `,` or parentheses.
- All app state stays under `~/.ao` (`CLAUDE.md` hard rule). The package writes only into the Arch prefix; it must never seed or touch `~/.ao`.
- `openapi.yaml` and `frontend/src/api/schema.ts` are generated. This plan does not touch the API surface.
- The package name is `agent-orchestrator-bin`; the binary name is `agent-orchestrator` (matching `EXECUTABLE_NAME` in `frontend/forge.config.ts`). Do not diverge: the desktop entry, the `/usr/bin` symlink and the deb payload all key off that name.
- Commit after each task.

## Tasks

### T1. Skeleton PKGBUILD that installs the released deb

- [ ] Create `packaging/arch/PKGBUILD` with `pkgname=agent-orchestrator-bin`, `pkgver` pinned to the current release (`0.10.3`), `arch=('x86_64')`, `license=('MIT')`, `url` pointing at the GitHub repo.
- [ ] `provides=('agent-orchestrator')`, `conflicts=('agent-orchestrator')` so a future source package can coexist in the AUR namespace.
- [ ] `source=("$pkgname-$pkgver.deb::https://github.com/Untrivial-ai/agent-orchestrator/releases/download/v$pkgver/agent-orchestrator-linux-x64.deb")` with a real `sha256sums`.
- [ ] `depends`: at minimum `gtk3`, `nss`, `alsa-lib`, `libxss`, `libnotify`, `xdg-utils`. Derive the real list by running `ldd` over the unpacked `resources/../agent-orchestrator` ELF rather than guessing.
- [ ] `package()` unpacks the deb (`bsdtar -xf data.tar.*`) and moves `usr/lib`, `usr/bin`, `usr/share` into `$pkgdir/usr/`.
- [ ] Check: `makepkg -f` produces a package; `pacman -Qlp` lists `/usr/bin/agent-orchestrator`, `/usr/lib/agent-orchestrator/agent-orchestrator`, `/usr/share/applications/*.desktop`, and hicolor icons.

### T2. chrome-sandbox permissions

Electron's SUID sandbox helper must be `root:root` mode `4755` or the app aborts at startup with "The SUID sandbox helper binary was found, but is not configured correctly".

- [ ] In `package()`, `chmod 4755 "$pkgdir/usr/lib/agent-orchestrator/chrome-sandbox"`.
- [ ] Do **not** add `--no-sandbox` to the launcher as a workaround. Arch enables unprivileged user namespaces by default, so the sandbox works; disabling it silently weakens the renderer.
- [ ] Check: launch the installed app and confirm no sandbox error on stderr, and that `pacman -Qkk agent-orchestrator-bin` reports no permission mismatch.

### T3. Put `ao` on PATH

The `ao` CLI and the daemon are the same Go binary (`backend/cmd/ao`), bundled by `frontend/scripts/build-daemon.mjs` into the app payload at `resources/daemon/ao`. It is not currently exposed on `PATH` by any Linux artifact, which is why `which ao` fails on a machine that runs the AppImage.

- [ ] In `package()`, symlink `/usr/bin/ao` at `/usr/lib/agent-orchestrator/resources/daemon/ao`. Confirm the exact in-payload path against the unpacked deb before hardcoding it.
- [ ] Confirm the binary is the full cobra CLI and not a daemon-only entrypoint (`ao --help` should list subcommands including `preview` and `start`).
- [ ] Decide and record whether `/usr/bin/ao` is too generic a name to claim in the Arch namespace. If it collides with an existing package, ship `agent-orchestrator-cli` instead and note it in the package README.
- [ ] Check: after install, `ao --version` and `ao preview https://example.com` both work from a shell.

### T4. Launcher entry, icon and the `ao-app://` scheme

- [ ] Verify the deb's own `/usr/share/applications/agent-orchestrator.desktop` is correct once relocated: `Exec` must be the `/usr/bin/agent-orchestrator` symlink, `Icon` the hicolor icon name, `Terminal=false`, and `MimeType` must include `x-scheme-handler/ao-app` (`forge.config.ts` passes `AUTH_PROTOCOL_MIME_TYPE` to the deb maker, so it should already be there).
- [ ] Create `packaging/arch/agent-orchestrator-bin.install` running `update-desktop-database` and `gtk-update-icon-cache` in `post_install`, `post_upgrade` and `post_remove`.
- [ ] Confirm interaction with the hidden entry `ao start` writes (`agent-orchestrator-ao-app.desktop`, `NoDisplay=true`, in `~/.local/share/applications`). Two entries claiming the same scheme means `xdg-mime` resolution order decides the winner. Determine whether the packaged entry should win, and if the user-level entry should be removed or left alone. Record the answer in the package README; do not silently delete a file the package does not own.
- [ ] Check: the app appears in the application launcher with its icon, launches on click with no terminal window, and `xdg-open ao-app://test` reaches the app.

### T5. Do not self-update a package-manager install

`initAutoUpdates()` in `frontend/src/main.ts:1963` starts electron-updater for every packaged build. On a pacman install the app lives under root-owned `/usr/lib`, so an update attempt either fails noisily or, worse, leaves `pacman`'s file database out of sync with what is on disk. The same latent bug already affects the published `.deb` and `.rpm`.

- [ ] Add a gate: skip the updater when the app is not running from an AppImage (`process.env.APPIMAGE` unset) and its own install directory is not writable by the current user. Put the predicate in `frontend/src/main/auto-updater.ts` so it is unit-testable, and call it from `initAutoUpdates`.
- [ ] Add vitest cases in `frontend/src/main/auto-updater.test.ts`: AppImage run updates; writable-dir run (macOS `/Applications`, Windows per-user) updates; root-owned-dir run does not.
- [ ] Surface a clear message in the UI's update panel for the skipped case ("Installed by your system package manager. Update with `pacman -Syu`.") rather than failing silently. Add the string to all 8 locales under `frontend/src/renderer/i18n/`.
- [ ] Check: the new tests pass, and a real pacman install shows the message instead of attempting a download.

### T6. Version-bump script and local verification runbook

- [ ] `packaging/arch/update-pkgbuild.sh`: read the latest release tag via `gh release view --json tagName`, rewrite `pkgver`, re-fetch the deb, recompute `sha256sums`, regenerate `.SRCINFO`.
- [ ] `packaging/arch/README.md` documenting the full loop: `makepkg -si`, launch, `pacman -Rns agent-orchestrator-bin`, and confirm nothing is left in `/usr` afterwards.
- [ ] Check: a clean install then removal leaves no orphan files (`pacman -Qo` on the former paths returns nothing) and does not touch `~/.ao`.

### T7. Publish to the AUR (gated on a decision)

- [ ] Confirm whether this package should be published to the AUR at all, and under whose account. An AUR package is a public maintenance commitment: it needs a `pkgver` bump on every upstream release or users get stale builds.
- [ ] If yes: create the AUR git remote, push `PKGBUILD` + `.SRCINFO`, and decide whether the release workflow should open a bump PR automatically or a human does it.
- [ ] If no: stop after T6. The in-repo `packaging/arch/` directory still gives anyone a one-command local install via `makepkg -si`.

### T8. Documentation

- [ ] Add an Arch row to the install table in `README.md` (around line 177, alongside the existing AppImage / Debian / Fedora rows).
- [ ] Note in `packaging/arch/README.md` that this is `x86_64` only, and why (see open questions).

## Risks

- **The `.deb` payload layout is assumed, not yet verified.** T1 must start by actually unpacking a released deb and listing it. Every path in T2 and T3 depends on what is really inside.
- **Bundled runtimes.** The app ships an agent-browser runtime (`prepare-agent-browser.mjs`) and an ACP runtime (`build-acp-runtime.mjs`) as `extraResource`. If either expects a writable directory next to itself, a root-owned `/usr/lib` install breaks it. Verify both at runtime, not just at launch.
- **Release cadence.** A `-bin` package pinned to a release tag goes stale the moment upstream cuts a new version. T6's script is the mitigation; T7 decides who runs it.

## Open questions

1. **AUR or local only?** Determines whether T7 happens and whether a maintenance commitment is being made.
2. **aarch64.** `build-artifacts.yml:52` has only a `linux-x64` matrix leg, so there is no arm64 deb to repackage. The Arch package is therefore `x86_64` only. Adding a `linux-arm64` leg is separate work; flag it if aarch64 support matters.
3. **`/usr/bin/ao` name claim.** See T3. Needs a check against the official repos and popular AUR packages before the name is taken.
4. **Should deb and rpm get the same T5 updater fix?** They have the identical latent bug. Fixing it once in `auto-updater.ts` covers all three, which argues for doing it properly rather than as an Arch-specific patch.
