AO Cloud POC Beta: Engineering Design

Move AO execution from the user's machine into isolated cloud sandboxes while preserving the existing product experience. Each agent session—including the orchestrator—runs in its own sandbox. An AWS-hosted AO control plane owns durable state, authentication, policy, and routing.

1. Executive summary

The POC will add Cloud projects beside AO's existing local projects. Execution location is a project-level invariant: a project is either entirely local or entirely Cloud, and its orchestrator and every child session inherit that choice. A Cloud project uses the authenticated AO API in AWS; creating any session in it directly provisions one sandbox, bootstraps an AO worker, clones the repository, and waits for the worker to report ready.

Core POC decision Provision synchronously from the create-session path. Do not run a background reconciler for this first beta. Persist the provider identity and the original error, then fix failures at their source instead of building a recovery system in advance.

Local and Cloud execution are never mixed inside one project. There is no session-level location selector and no path for a Cloud orchestrator to create a local child (or the reverse). Moving work between locations means creating a separate project.

Harness authentication should feel equally continuous. If Claude Code or Codex is already connected on the user's computer, AO offers one explicit “Use in Cloud” action. The user does not copy an API key or sign in again for every project or sandbox. The connection is encrypted once at user scope and delivered only to that user's authenticated Cloud workers.

The initial Cloud agent catalog contains exactly two harnesses: claude-code and codex. Other harnesses that AO supports locally remain local-only until we intentionally add and verify them in Cloud.

We will reuse the private ao-cloud control plane, PostgreSQL model, provider adapters, worker protocol, GitHub brokering, and shared product UI. The implementation change is to introduce a small direct provisioner and route the POC session-creation path through it, without depending on the existing reconciliation scheduler.

2. Context and starting point

2.1 Current local model

Today, the desktop supervises a loopback AO daemon. The daemon owns local SQLite state and starts agent processes in local worktrees. Terminal, files, diffs, browser sessions, Git operations, and agent lifecycle all depend on the user's machine.

2.2 Desired Cloud model

The Cloud product should preserve the interaction model while changing the execution location. Users still create projects, create sessions, send prompts, inspect activity, open terminals, review files and diffs, and work with pull requests. The difference is that each session has isolated cloud compute and a durable control-plane identity.

3. Goals and non-goals

POC must prove

  • A user can create a Cloud project and orchestrator session.
  • The orchestrator runs in its own sandbox.
  • The orchestrator can spawn a child session in a different sandbox.
  • Prompts, activity, files, diffs, and terminal traffic cross the Cloud boundary.
  • A worker can clone the approved repository and push its own branch.
  • Infrastructure credentials never enter a sandbox; harness auth is confined to that session's process/home and never enters the workspace or another session.
  • Feature-off behavior and sandbox teardown are safe and observable.
  • The existing local AO path does not regress.
  • A project and all of its sessions use exactly one execution location.
  • A user connects each harness once and can use it across their Cloud projects.
  • No sandbox requires a separate interactive harness login.
  • Claude Code and Codex both complete the Cloud session lifecycle.

Not required for the first beta

  • Automatic repair, reconciliation, orphan collection, or self-healing.
  • Automatic pause/resume and cost optimization.
  • Multiple sandbox providers in production.
  • Multi-region placement, warm pools, or formal availability targets.
  • Billing, metering, or broad self-service onboarding.
  • Moving an existing project or session between local and Cloud.
  • Any agent harness beyond Claude Code and Codex.
  • Native agent-TUI attachment if chat and workspace terminal satisfy the POC.

4. Engineering decisions

IDDecisionReasoningConsequence
D1Run the AO control plane in AWS; keep PostgreSQL as durable authority.Cloud clients and workers need a common tenant-aware authority that survives sandbox replacement.API replicas remain stateless between requests; no sandbox filesystem is authoritative.
D2Allocate exactly one sandbox per agent session, including orchestrators.This matches AO's session isolation model and prevents branches, agent homes, terminals, or secrets from leaking between sessions.An orchestrator is a normal session with extra scoped orchestration permissions, not privileged shared compute.
D3Workers initiate outbound HTTPS/WebSocket connections to the control plane.It avoids public ingress to sandboxes and works across providers with different network models.The worker polls or streams commands; the control plane never depends on a routable sandbox address for normal operation.
D4Provision directly in the session-creation request; omit the reconciler.The beta needs the shortest debuggable path. A controller adds leases, scheduling, retry policy, and asynchronous state transitions before we have real failure data.Creation can take tens of seconds. A failure is surfaced directly so we can diagnose and fix its cause.
D5Keep the provider-neutral interface, but launch with one already-integrated hosted provider.Provider-neutral domain types are already present; building a second provider before the first live loop works delays learning.Use the existing hosted nodeops path first. Evaluate Daytona only if the live probe exposes a blocking limitation.
D6Choose execution location at project creation and never mix locations within a project.Project-scoped orchestration, repository state, session listing, and lifecycle remain much simpler when every session has the same host.execution_location is local or cloud, is not editable, and is inherited by orchestrators and children. Sessions have no location selector.
D7Reuse shared Cloud contracts and product UI through host adapters.Local and Cloud should present one AO product without making the local daemon switch transports internally.The local adapter continues calling loopback APIs; the Cloud adapter calls authenticated hosted APIs.
D8Use one-time bootstrap tickets and scoped, just-in-time credentials.A sandbox needs harness auth to run the agent, but it never needs AWS, database, sandbox-provider, WorkOS, or GitHub App authority.The control plane brokers only the selected harness credential and operation-specific grants to the current worker epoch.
D9Persist lifecycle facts; derive user-facing status.“Running” must mean the AO worker is usable, not merely that the provider reports a booted VM.Provider state, worker readiness, turn state, and errors remain separate facts. UI labels are computed from them.
D10Do not build generalized failure handling yet.We do not know which failures will occur in practice or which ones will remain after their root causes are fixed.The POC records and returns the real provider or worker error. We add a targeted recovery path only for a recurring failure that cannot reasonably be eliminated.
D11Make harness subscription auth a one-time, user-scoped Cloud connection.Requiring API keys, repeated device login, or per-project setup would make Cloud feel worse than local AO.The desktop can import a supported local subscription credential with consent. Cloud stores it encrypted once and brokers it to the user's current sandbox when a turn starts.
D12Launch with a closed Cloud catalog of Claude Code and Codex.Each harness needs its own image installation, auth bridge, launch policy, event handling, and acceptance coverage. Adding the entire local catalog would multiply the POC surface.Cloud project/session APIs reject every other harness. Local AO's broader catalog is unchanged. New Cloud harnesses are added one at a time after conformance and hosted acceptance.

to the caller. The next step is diagnosis and a root-cause fix, not automatic recovery.

6.2 Provisioner algorithm

  1. Validate. Require a Cloud project, organization access, a healthy configured provider, claude-code or codex, and an idempotency key.
  2. Reserve. In one transaction, create or replay the command receipt, session, branch, initial turn/event, sandbox record, and organization quota reservation.
  3. Create. Call Provider.Create outside the transaction with a deterministic session name and labels containing environment, organization, and session identifiers.
  4. Persist identity. Store the provider environment ID immediately after it is returned, before worker upload or bootstrap.
  5. Bootstrap. Mint a one-time ticket, construct the worker specification, install/start the AO worker, and let it redeem the ticket for an epoch-scoped credential.
  6. Materialize. The worker obtains a short-lived checkout grant, validates repository identity, clones the repository, and starts the selected agent.
  7. Resolve. Wait up to a bounded deadline for worker readiness. Mark the sandbox running or failed, retain the original error, and return the session.

6.3 State model

                  ▼                   ▼             ▼

User-facing labels are derived from these lifecycle facts plus worker/turn facts.
The session table does not persist a separate display status.

6.4 Failure policy

Keep failure handling intentionally small. Preserve AO's existing command idempotency so a repeated client request returns the original result. Use the session ID in the provider name or labels so a sandbox can be identified during debugging. Beyond that:

  • Return the underlying provider or worker error with the session and request IDs.
  • Inspect the logs and provider state.
  • Fix the configuration, image, network, credential, quota, or code issue that caused it.
  • Clean up a partially created sandbox manually before trying again.
  • Add automated handling only when the same unavoidable failure recurs.
Accepted POC limitation A failed attempt may require inspecting or deleting a sandbox in the provider console. That is acceptable for an internal beta. We will not build a generic retry, repair, or orphan-recovery framework until actual experience requires one.

6.5 Deletion

Deletion is also direct. Mark deletion requested, call the provider with the stored ID (or unique session label), confirm absence using ErrNotFound, and then record deleted. A failed or unknown provider probe is not proof that compute is gone. The durable session transcript may remain after compute is deleted.

7. Worker protocol and product experience

7.1 Worker bootstrap

  • The control plane creates a short-lived, single-use bootstrap ticket and stores only its hash.
  • The ticket is bound to organization, session, purpose, worker epoch, and expiry.
  • The worker redeems it over TLS and receives only the scopes needed for that session.
  • A replacement worker increments the epoch; older workers cannot claim or complete new work.
  • The worker reports ready only after its workspace and agent runtime are usable.

The worker requests the credential when it is about to run the harness. It does not
receive provider secrets in its bootstrap environment or sandbox-provider metadata.
Sandbox exposure boundary The harness must receive a usable subscription credential, so processes running as that sandbox user may be able to read it. The POC confines the credential to one session's harness process or private harness home. It is never baked into an image, placed in the repository workspace, sent through provider metadata, shared across users, or written to AO logs/events. Deleting the sandbox deletes its local copy.

Storage and ownership

  • The connection belongs to the AO user, not to a project or sandbox, so one connection works across all of that user's Cloud projects.
  • The Cloud API validates the credential before saving it and stores authenticated ciphertext plus a nonce in the existing user-provider connection record.
  • Encryption associated data binds the ciphertext to the user, harness, and connection label, preventing it from being moved to another owner or provider.
  • API responses expose only provider, account/plan metadata when available, validation state, and last-updated time—never the secret.
  • An organization-managed harness credential may be added later; the POC defaults to the session creator's personal subscription.

Desktop credential bridge

  • Each harness gets a small adapter that can detect local sign-in and obtain only an officially portable token or credential bundle.
  • The adapter runs in Electron main (or another privileged native process), where AO already keeps Cloud account tokens. The renderer can request an import but cannot read its result.
  • Do not upload the harness's entire home directory. Settings, MCP configuration, conversation history, project trust, and telemetry identifiers are not authentication and stay local.
  • Do not depend on undocumented keychain item names or blindly scrape arbitrary files. If a harness does not expose a safe portable credential, AO launches that harness's official browser/device login once and stores the resulting Cloud connection.

Expiration and reconnect UX

The POC does not add background token-refresh infrastructure. The harness uses the imported subscription credential normally. If the provider rejects it, AO marks the user connection as needing reconnection and shows one action: Reconnect Claude Code or Reconnect Codex. Reconnecting replaces the encrypted user connection; because workers fetch the credential when starting a turn, the next turn uses the new value without recreating projects or sandboxes.

9. Data and API changes

9.1 Data model

Reuse the existing session, sandbox, access-ticket, worker-epoch, command-receipt, turn, event, and audit records. The POC should avoid a new job queue or lease table. The direct provisioner needs these facts:

FactPurpose
project.execution_locationImmutable local or cloud project boundary inherited by every session
user_provider_connectionUser-scoped encrypted harness subscription credential, reusable across the user's Cloud projects
session_id, org_id, project_idStable ownership and provider labels
provider, provider_environment_idLocate and operate the sandbox
observed_state, last_error, timestampsExpose factual lifecycle progress and the original failure
worker_epoch, worker_last_seen_atReadiness and stale-worker fencing
idempotency command receiptReturn the original result for repeated create input
resource and bootstrap contextConstruct a reproducible provider and worker request without storing plaintext secrets

9.2 API behavior

  • Project creation requires execution_location. Local hosts create local projects; the Cloud host creates cloud projects. The field is immutable.
  • The desktop can create or replace the signed-in user's harness connection over an authenticated, no-store endpoint. The renderer can list connection metadata but never read the secret.
  • POST /orgs/{orgId}/sessions retains its required Idempotency-Key, loads the parent project, and provisions a sandbox only for a Cloud project.
  • The create response includes the session projection and factual sandbox progress. If the existing contract can represent this, do not add a second POC-only DTO.
  • Orchestrator child-session routes call the same creation service and enforce same-organization, same-project scope. They inherit location from the project.

10. Implementation plan

Slice 0 — Establish the live baseline

  • Initialize the private ao-cloud checkout at the compatible commit.
  • Run its unit/integration suite and local Docker lifecycle acceptance.
  • Configure staging AWS, WorkOS, GitHub, and hosted-provider credentials without writing them to the repository.
  • Verify staging API/database health and run a read-only provider capability probe.

Slice 1 — Add project location and the direct provisioner

  • Add immutable execution_location to the shared project model and creation flow.
  • Make session and orchestrator creation inherit location from the parent project.
  • Add desktop credential bridges for Claude Code and Codex; keep both secrets out of the renderer.
  • Make the Cloud catalog return only claude-code and codex; reject other harness IDs at session creation.
  • Do not start the sandbox reconciler for direct-POC deployments.
  • Extract provider create/bootstrap logic into a small service callable from the HTTP session path.
  • Reuse internal/sandbox.Provider, bootstrap-ticket creation, worker-spec construction, quota reservation, and epoch fencing.
  • Label the provider environment with the session ID and persist its ID before bootstrap.
  • Add bounded create and readiness deadlines; return the original failure clearly.

Likely private code areas: cmd/ao-cloud/main.go, internal/httpapi/resource_handlers.go, a small direct-provisioning service, internal/postgres/sandbox_store.go, and existing internal/sandbox/* adapters. Contract artifacts change only if the current session projection cannot express provisioning facts.

Slice 2 — Complete one hosted session

  • Create one Cloud project and session against the live hosted provider.
  • Connect each user's local Claude Code and Codex subscription once and verify each sandbox starts without another login prompt.
  • Redeem the worker ticket, clone an approved repository, and report ready.
  • Send an initial and follow-up prompt; verify durable event replay after reconnect.
  • Inspect files and diff, open a workspace terminal, and push a branch.
  • Delete the sandbox and confirm provider absence without deleting durable history.

Slice 3 — Prove orchestrator fan-out

  • Provision an orchestrator through the same session path.
  • Give it only project-scoped list/create/message/observe permissions.
  • Have it create one child; confirm distinct provider IDs, workspaces, branches, homes, and worker credentials.
  • Have the orchestrator message the child and observe its durable progress.
  • Confirm a cross-project or cross-organization child request fails closed.

Slice 4 — Expose the hidden beta

  • Render local or Cloud controls from the selected project's execution location.
  • Show provisioning, running, and failed states with the original actionable error.
  • Document the single manual cleanup procedure used during the internal beta.
  • Add basic logs and timing for provisioning and worker readiness.
  • Verify a project cannot contain sessions from both locations.

Implementation rule

Each slice ends with a real, inspectable result. We do not build later lifecycle automation until the preceding vertical path works against the actual hosted provider.

11.2 Beta release gates

  • E2E: one internal user completes the full hosted loop.
  • 1 → N: one sandboxed orchestrator creates and controls at least one isolated child.
  • PROJECT BOUNDARY: local and Cloud projects work independently; neither can create a session in the other location.
  • SECURITY: credential logs and sandbox environments contain no long-lived control-plane secret.
  • ONBOARDING: for both Claude Code and Codex, a locally authenticated user connects once and starts an orchestrator plus child without copying a key or repeating provider login.
  • CLEANUP: every test sandbox is accounted for by session ID and can be deleted deterministically.

11.3 Minimum debugging signal

Every provisioning attempt should produce one structured log trail containing:

  • request ID, organization ID, session ID, provider, release, and attempt;
  • time spent reserving, creating, persisting identity, bootstrapping, checkout, and waiting for ready;
  • provider result class without credential or prompt content;
  • the original provider, bootstrap, checkout, or readiness error.

11.4 Rollback

  1. Stop creating new Cloud projects in the internal POC environment.
  2. Use session/provider IDs to delete active test sandboxes explicitly.
  3. Roll back the application image; do not reverse compatible database migrations.

12. When to add a reconciler

A reconciler is a background control loop that repeatedly compares desired state (“this sandbox should be running”) with observed provider state and performs the next safe action. It becomes valuable when lifecycle operations must continue after an HTTP request or process ends.

It was part of the earlier design because the production target implies provider timeouts, API restarts, multiple replicas, automatic resume, replacement workers, cleanup, and eventual consistency. The existing private implementation also already uses that architecture. Those are legitimate production concerns, but they are not prerequisites for learning from a tightly controlled POC.

Decision Do not schedule reconciler work in the initial implementation. Revisit it only when observed operations or a committed product requirement makes synchronous manual handling inadequate.

Concrete triggers for revisiting the decision

  • Provider calls regularly outlive the API request budget.
  • Orphaned or duplicate sandboxes recur after their immediate causes have been fixed.
  • Automatic pause/resume, replacement, or crash recovery becomes a beta requirement.
  • Provisioning must remain correct across multiple active API replicas.
  • Operators spend meaningful time retrying or cleaning up sessions.
  • Users need creation to return immediately while work continues reliably in the background.

If triggered, the direct provisioner should become the operation primitive used by a controller rather than being discarded. The later reconciler would add durable scheduling, leases, backoff, and convergence around the same provider and bootstrap services.
