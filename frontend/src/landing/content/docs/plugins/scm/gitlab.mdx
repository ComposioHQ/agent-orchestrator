title: GitLab SCM
description: Merge request observation, lifecycle feedback, and self-managed instance support.
---

AO observes GitLab merge requests through the same provider-neutral SCM lane as GitHub. Both providers run side by side: a repository is routed by its remote, and a provider without usable credentials is skipped rather than breaking the other.

The provider tracks merge request identity and state (including drafts), CI pipeline status and failing job names, approval state, and mergeability with conflict reasons. Explicit actions are merge, request review, and resolve review threads.

Use `ao doctor` to inspect local GitLab readiness.

## Authentication

The token is resolved in order from `AO_GITLAB_TOKEN`, `GITLAB_TOKEN`, then `glab auth status --show-token`. A personal access token needs `api` scope.

## Self-managed instances

gitlab.com works with no configuration. Self-managed hosts must be allowlisted — an unlisted host is rejected before any credential is attached, so AO never sends your gitlab.com token to an arbitrary server:

```bash
export AO_GITLAB_ALLOWED_HOSTS="gitlab.example.com,gitlab.internal:8443"
```

Each host may carry a port. When one instance needs its own token, map it per host; hosts without an entry fall back to the default token above:

```bash
export AO_GITLAB_HOST_TOKENS="gitlab.example.com=glpat-xxx,gitlab.internal:8443=glpat-yyy"
```

Both variables are read once at daemon startup, so restart the daemon after changing them. Export them from your shell profile (`~/.zshrc`, `~/.zprofile`, or the equivalent): the desktop app resolves your login-shell environment before spawning the daemon, so a profile export reaches a Finder or Dock launch too. Setting them only in an ad-hoc terminal leaves a desktop-launched daemon without them.

`ao doctor` reports one check per instance — `gitlab-token` for gitlab.com and `gitlab-token:<host>` for each allowlisted host — so a token that is valid on one instance and rejected on another is visible per host. A self-managed host that is unreachable from where you are (VPN down, split DNS) is a warning, not a failure: it says nothing about the credential.

Doctor only sends a token to the instance it can attribute it to, and reports the probe as skipped otherwise — it never validates one instance's credential against another's API. A token counts as attributed when it comes from that host's `AO_GITLAB_HOST_TOKENS` entry, from `glab auth status --hostname <host>`, or from `AO_GITLAB_TOKEN`/`GITLAB_TOKEN` (which you declared as the default for every instance). Two cases are therefore reported rather than probed: the shared default token also authenticating an allowlisted host, and `glab` answering for its own default host instead of the one being checked. Give each instance its own credential — `glab auth login --hostname <host>`, or an `AO_GITLAB_HOST_TOKENS` entry — to have every host validated.

The daemon applies the same rule to gitlab.com: once a self-managed host is allowlisted, gitlab.com is authenticated only with `AO_GITLAB_TOKEN`/`GITLAB_TOKEN` or with `glab auth login --hostname gitlab.com` — never with `glab`'s default-host token, which may belong to your internal instance. For the self-managed hosts themselves the daemon is less strict than doctor: a host with no credential of its own still falls back to `glab`'s default-host token at runtime, which is why doctor flags that setup instead of silently confirming it.

<Callout type="warn">
	Self-managed API traffic is always `https://<host>/api/v4`. Instances served over plain HTTP, or under a path prefix such as `https://host/gitlab`, are not supported. A private certificate authority must be trusted by the operating system — AO has no separate CA setting.
</Callout>

Agents running inside a worker use their own tooling. If your agent shells out to `glab`, configure it for your instance (`glab auth login --hostname gitlab.example.com`, or export `GLAB_HOST`); AO does not set that for the session.
