title: GitLab issue intake
description: Read-only GitLab issue lookup for spawn bootstrap and opt-in intake.
---

The GitLab tracker reads issues from gitlab.com and from allowlisted self-managed instances. It shares the SCM provider's token chain: `AO_GITLAB_TOKEN`, `GITLAB_TOKEN`, then `glab auth status --show-token`.

## Hydrate a worker from an issue

```bash
ao spawn --project my-app --name fix-login --tracker-provider gitlab --issue 42
```

The issue snapshot is read once to seed the agent prompt.

## Opt-in intake

Intake polls a project's tracker scope and can create workers for matching issues. The `ao project set-config` flags always record the `github` provider; selecting GitLab needs the full object:

```bash
ao project set-config my-app --config-json '{
  "trackerIntake": {
    "enabled": true,
    "provider": "gitlab",
    "repo": "group/subgroup/project",
    "assignee": "alice"
  }
}'
```

Self-managed hosts are derived from the project's Git remote and must appear in `AO_GITLAB_ALLOWED_HOSTS`; see [GitLab SCM](/docs/plugins/scm/gitlab) for host and per-host token configuration.

## Current boundary

The adapter is read-only: it fetches and lists issues, and never comments, transitions, or closes them. Unlike the GitHub tracker it does no conditional revalidation, so every list is a fresh fetch. Merge requests, CI, and reviews belong to the separate [GitLab SCM capability](/docs/plugins/scm/gitlab).
